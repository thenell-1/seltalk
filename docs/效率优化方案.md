## 一、现状梳理与瓶颈识别

### 1.1 端到端工作流全景

主链路 `orchestrator::trigger` 共 9 步，从热键按下到候选就绪：

| 步骤 | 操作 | 代码位置 | 典型耗时 |
|------|------|----------|----------|
| 1 | 获取任务锁（含看门狗） | `orchestrator/mod.rs` `acquire_with_watchdog` | μs 级 |
| 2 | 重置中断 + 记录目标 HWND + 诊断日志 | `orchestrator/mod.rs` L127-137 | μs 级 |
| 3 | 刷新配置缓存（DB lock + 全量加载） | `orchestrator/mod.rs` L140-162 | 1~5ms |
| 4 | 读取剪贴板纯文本 | `clipboard::read_text_or_empty` | <10ms |
| 5 | 清洗文本 | `text::clean::clean` | μs 级 |
| 6 | emit loading + 显示悬浮窗 | `orchestrator/mod.rs` L178-181 | 5~20ms |
| 7 | 加载黑名单（解析 JSON+编译正则）+ 词库 | `orchestrator/mod.rs` L184-210 | 2~10ms |
| 8 | **LLM 生成候选** | `orchestrator/mod.rs` L218 | **300ms~5s+** |
| 9 | emit ready | `orchestrator/mod.rs` L241 | μs 级 |

确认链路 `do_type_candidate`：隐藏悬浮窗 → `sleep 120ms` → **逐字输入（30~120ms/字）** → 词频记录（同步 DB 写入）。

取消链路 `do_cancel`：设置中断标志 → 输入中等待中断生效 / 显示中隐藏悬浮窗 + 释放锁。

### 1.2 五大关键瓶颈（按影响排序）

#### 瓶颈①：LLM 单次同步阻塞请求（最大瓶颈）

- `llm/client::chat` 为非流式请求，`max_tokens=1024`（`config.rs:27`），用户须等整段生成完毕才能看到候选。**首字延迟 ≈ 总生成时间**。
- 候选数通过 Prompt 内 `---` 分隔实现（`llm/mod.rs:50`），依赖 LLM 遵守格式，切分易异常（`text/split.rs`）。
- 无重试、无流式、无缓存、无超时分级。

#### 瓶颈②：每次触发重复加载配置/模板/黑名单/词库

- `trigger` 步骤 3 每次全量 `load_config_from_db`，即便已有 `config_cache`。
- `generate_candidates` 每次从 DB 加载 LLM 配置 + 默认模板（`llm/mod.rs:31-41`）。
- 步骤 7 每次解析黑名单 JSON + 编译正则 + 查询词库拼接。

#### 瓶颈③：逐字输入累积延迟

- `type_text` 每字 30~120ms 随机延迟，100 字累计 3~12s。
- 每字都调用 `get_foreground_hwnd`（Win32 API）做焦点检测，无降频。

#### 瓶颈④：词频记录阻塞主链路返回

- `do_type_candidate` L294-302 在确认完成后**同步**执行分词 + 批量入库，占用 DB 锁，延迟下一次触发的响应。

#### 瓶颈⑤：悬浮窗显示链路多次 DB/窗口操作

- `show_float` 虽已优化，仍包含 `load_state`（DB）+ `correct_boundary`（get_float + current_monitor）+ `apply_state`（3 次窗口调用）+ `show` + `set_focus` + `save_state`（DB）。

### 1.3 已具备的基础设施

- ✅ 任务锁 + 看门狗（`state/task_lock`）
- ✅ 配置缓存 `config_cache`（`state/mod.rs`）
- ✅ HTTP 连接复用 `reqwest::Client`（`state/mod.rs`）
- ✅ 异步主链路（`tauri::async_runtime::spawn`）
- ✅ 悬浮窗 loading/ready/error 三态（`float/App.vue`）
- ✅ 日志体系 `tracing` + 文件轮转

## 二、流程优化措施

### 2.1 配置/模板/黑名单/词库缓存（P0，消除重复 DB）

**目标**：避免每次触发重复加载，采用"写时失效"策略。

**设计**：在 `state::AppState` 新增缓存字段与版本号：

```rust
// state/mod.rs 新增字段
pub struct AppState {
    // ... 现有字段
    /// LLM 配置缓存（含 base_url/api_key/model/temperature/max_tokens）
    pub llm_cfg_cache: RwLock<LlmConfig>,
    /// 默认模板缓存
    pub prompt_cache: RwLock<Option<String>>,
    /// 黑名单编译后的正则缓存（变更时失效）
    pub blacklist_cache: RwLock<Vec<regex::Regex>>,
    /// 启用词库拼接字符串缓存
    pub words_cache: RwLock<String>,
    /// 配置版本号（任何设置变更时 +1，用于快速判断是否需要重载）
    pub config_version: AtomicU64,
}
```

**失效策略**：

- `set_setting` / `prompt_set_default` / `blacklist_set` / `word_*` 命令执行时递增 `config_version`。
- `trigger` 入口仅比较版本号，未变则跳过步骤 3/7 的 DB 加载。

**预期收益**：每次触发减少 3~4 次 DB lock + 1 次正则编译，节省 3~15ms。

### 2.2 词频记录异步化（P0）

**目标**：将词频记录从 `do_type_candidate` 主路径剥离，确认输入后立即返回。

**设计**：

```rust
// orchestrator/mod.rs do_type_candidate 末尾
let words = text::wordcloud::extract_words(text);
if !words.is_empty() {
    let app_clone = app.clone();
    tauri::async_runtime::spawn(async move {
        // 在 spawn_blocking 中执行 DB 写入，不阻塞命令返回
        let _ = tokio::task::spawn_blocking(move || {
            // 通过 app_clone.state::<AppState>() 获取 db 并写入
            // word_freq::record_batch(&db, &words)
        }).await;
    });
}
```

**注意点**：进程退出前需确保落盘（启动时 flush 队列 + 退出钩子）。

**预期收益**：确认输入命令立即返回，下一次触发的锁竞争减少。

### 2.3 悬浮窗显示链路精简（P1）

**目标**：减少 `show_float` 中的重复 DB/窗口操作。

**设计**：

- 启动时已 `restore_on_startup`，窗口尺寸/位置/置顶已应用。
- 新增 `AtomicBool state_applied` 标记"窗口状态是否已应用"。
- `show_float` 在 `state_applied == true` 时，跳过 `load_state + apply_state`，仅 `show + set_focus`。
- 拖拽/缩放结束（`save_float_state` 命令）后置 `state_applied = false`，下次显示重新应用。

**预期收益**：常规触发节省 1 次 DB 读 + 3 次窗口调用，约 3~10ms。

### 2.4 剪贴板上下文复用（P1）

**目标**：避免每次新建 `ClipboardContext`。

**设计**：`clipboard_rs::ClipboardContext` 是 `Send` 但非 `Sync`，用 `Mutex<ClipboardContext>` 包裹后存入 `OnceLock` 全局复用。

```rust
// clipboard/mod.rs
static CLIP_CTX: OnceLock<Mutex<ClipboardContext>> = OnceLock::new();

fn with_ctx<F, R>(f: F) -> AppResult<R>
where F: FnOnce(&ClipboardContext) -> AppResult<R> {
    let ctx_mutex = CLIP_CTX.get_or_try_init(|| {
        ClipboardContext::new()
            .map(Mutex::new)
            .map_err(|e| AppError::Clipboard(format!("剪贴板初始化失败: {e}")))
    })?;
    let ctx = ctx_mutex.lock()
        .map_err(|e| AppError::Clipboard(format!("剪贴板锁中毒: {e}")))?;
    f(&ctx)
}
```

**预期收益**：消除重复初始化，约 1~3ms/次。

### 2.5 减少不必要环节（P1）

- `trigger` 步骤 3 的全量配置刷新改为"仅在 `config_version` 变化时刷新"。
- 步骤 2 的诊断日志 `get_foreground_title` 每次调用 Win32 API，降级为 `debug` 级别且仅在开启诊断时调用。

### 2.6 逐字输入焦点检测降频（P1）

**目标**：减少每字一次的 Win32 API 调用。

**设计**：[input/mod.rs](file:///d:/vibecoding/择言（SelTalk）/src-tauri/src/input/mod.rs) `type_text` 中，焦点检测改为每 N 字一次（N=5），或基于时间间隔（每 200ms 一次）。

```rust
const FOCUS_CHECK_INTERVAL: usize = 5;
for (i, ch) in normalized.chars().enumerate() {
    // 焦点检测降频：每 5 字或首字检查
    if i % FOCUS_CHECK_INTERVAL == 0 {
        let current_hwnd = sendinput::get_foreground_hwnd();
        if focus_hwnd != 0 && current_hwnd != focus_hwnd {
            return Err(AppError::Input(format!(
                "焦点已漂移: 预期 {focus_hwnd}, 当前 {current_hwnd}"
            )));
        }
    }
    // ... 发送字符
}
```

**预期收益**：长文本输入减少 ~80% 的焦点检测 API 调用。

## 三、模型输出性能评估与分析

### 3.1 影响速度的关键因素

| 因素 | 当前状态 | 影响 |
|------|----------|------|
| 流式输出 | ❌ 非流式 | 首字延迟 = 总生成时间 |
| max_tokens | 1024（固定） | 短回复场景浪费，长回复场景可能截断 |
| temperature | 0.8（固定） | 偏高，易生成冗长内容拖慢输出 |
| 候选切分 | Prompt 内 `---` 分隔 | 依赖 LLM 格式遵守，切分异常需重试 |
| 重试机制 | ❌ 无 | 网络抖动直接失败 |
| 超时控制 | 单一 30s | 无法区分连接超时与读超时 |
| 结果缓存 | ❌ 无 | 相同输入重复请求 |
| 连接复用 | ✅ reqwest::Client | 已优化 |

### 3.2 性能评估手段（埋点）

在 `llm/client::chat` 增加分阶段计时：

```rust
let t_start = Instant::now();
let resp = client.post(&url).bearer_auth(&cfg.api_key).json(req).send().await?;
let t_first_byte = Instant::now();  // 连接+请求耗时
let body = resp.json::<ChatResponse>().await?;
let t_complete = Instant::now();    // 解析完成
tracing::info!(
    "LLM 耗时: 连接={}ms 总={}ms 输入={}字 输出={}字",
    t_first_byte.duration_since(t_start).as_millis(),
    t_complete.duration_since(t_start).as_millis(),
    req.messages.iter().map(|m| m.content.chars().count()).sum::<usize>(),
    body.choices.iter().map(|c| c.message.content.chars().count()).sum::<usize>(),
);
```

### 3.3 评估结论

LLM 请求是绝对主瓶颈，占总耗时 90%+。优化重心应放在：流式输出（降低感知延迟）+ 缓存（减少请求次数）+ 参数调优（减少生成量）。

## 四、模型优化策略

### 4.1 流式输出（P0，最高收益）

**目标**：首字延迟从"总生成时间"降到"首 token 时间"（通常 <500ms）。

**设计**：

- 改造 `llm/client::chat` 支持 SSE 流式：请求加 `"stream": true`，`reqwest` 用 `bytes_stream()` 逐行解析 SSE。
- `trigger` 改为流式接收，候选边生成边通过 `emit_to("candidates-stream", chunk)` 推送前端，悬浮窗渐进显示。
- 完成后再用 `text/split.rs` 切分最终候选。
- `float/App.vue` 新增 `onCandidatesStream` 监听，渐进拼接显示。

**回退策略**：新增配置开关 `llm_stream_enabled`（默认 true），关闭时走原非流式分支。

### 4.2 参数调优（P0）

- `max_tokens` 按 `candidate_count` 动态计算：`n * 80 + 100`（每条约 80 字 + 余量），避免固定 1024。
- `temperature` 默认从 0.8 降到 0.6，减少冗长发散。
- 新增 `top_p` 配置项，支持 nucleus sampling。

### 4.3 候选缓存（P1）

**目标**：相同输入命中缓存时跳过 LLM 请求。

**设计**：LRU 缓存，key = `(model, template_hash, cleaned_text_hash, words_hash)`，TTL 10 分钟：

```rust
pub struct CandidateCache {
    map: Mutex<LruCache<u64, CachedEntry>>,
}

struct CachedEntry {
    candidates: Vec<String>,
    inserted_at: Instant,
}
```

**失效策略**：`config_version` 变化时清空缓存。

### 4.4 重试 + 超时分级（P1）

- 连接超时 5s / 读超时 30s 分离（`reqwest::Client::builder().connect_timeout().timeout()`）。
- 网络错误（非 4xx 业务错误）自动重试 1 次，指数退避。
- 5xx 重试，4xx 不重试（业务错误）。

### 4.5 Prompt 格式鲁棒性（P2）

当前依赖 `---` 分隔。增强：

- Prompt 明确要求"每条候选以 `---` 开头独占一行"。
- 切分增加编号兜底（`1. 2. 3.`）。
- 若 API 支持 `n` 参数，优先用 `n` 而非 Prompt 分隔（`llm/types.rs` 已留 `n: Option<u32>` 字段，可启用）。

### 4.6 连接预热（P2）

启动时 `spawn` 一个轻量 ping 请求（复用 `test_connection`），预热 DNS + TLS 握手 + 连接池，首次真实请求更快。

## 五、效率监测指标体系

### 5.1 核心指标定义

| 指标 | 定义 | 采集点 | 目标值 |
|------|------|--------|--------|
| TTFR（首响应时间） | 热键按下→悬浮窗显示 | trigger 入口/步骤6 | <1s（已达成） |
| TTFR_ready（首候选时间） | 热键按下→首候选可见 | trigger 入口/步骤9 | <2s（流式后） |
| LLM 首字节延迟 | 请求发出→首 token | client.rs 埋点 | <500ms |
| LLM 总耗时 | 请求发出→响应完成 | client.rs 埋点 | <3s |
| 输入吞吐 | 逐字输入字数/秒 | type_text 埋点 | ≥15 字/秒 |
| 缓存命中率 | 候选缓存命中/总请求 | CandidateCache | ≥20% |
| DB 锁等待 | db.lock() 等待时长 | 包装 Mutex | <5ms |
| 错误率 | LLM 失败次数/总请求 | client.rs | <2% |
| 重试触发率 | 重试次数/总请求 | client.rs | <5% |

### 5.2 采集实现

- 用 `tracing` 的 `span` + `Instant` 埋点，写入日志文件。
- 新增 `metrics` 内存计数器（`AtomicU64`），通过 `get_metrics` 命令暴露给设置页"性能"面板，前端可视化。
- 关键 span：`trigger`、`llm_chat`、`type_text`、`db_lock`。

### 5.3 定期跟踪

- 日志按天轮转（已有 `LOG_KEEP_DAYS=7`）。
- 设置页新增"性能概览"：展示近 24h 平均 TTFR / LLM 耗时 / 错误率 / 缓存命中率。

## 六、持续改进计划

### 6.1 实施阶段划分

| 阶段 | 内容 | 预期收益 | 工期估算 |
|------|------|----------|----------|
| **P0** | 流式输出 + 配置缓存 + 词频异步化 + 参数调优 | TTFR_ready <2s，重复触发更快 | 1~2 天 |
| **P1** | 候选缓存 + 重试/超时分级 + 悬浮窗精简 + 焦点检测降频 + 性能埋点 | 错误率<2%，输入提速 | 2~3 天 |
| **P2** | n 参数并发 + Prompt 鲁棒性 + 连接预热 + 性能面板 | 边际优化，可观测性 | 按需 |

### 6.2 长期维持机制

1. **回归基线**：P0 完成后建立性能基线，后续改动用 `cargo bench` + 端到端用例校验不退化。
2. **CI 守护**：Clippy + vue-tsc + 单测（已有），新增 LLM mock 的集成测试，断言流式首字延迟。
3. **指标巡检**：每周 review `get_metrics` 输出，异常波动定位。
4. **配置可调**：`max_tokens`/`temperature`/缓存 TTL/重试次数全部走 settings 表，前端可配，无需改代码。

### 6.3 风险与回退

| 风险 | 影响 | 缓解措施 |
|------|------|----------|
| 流式改造涉及三处（client/orchestrator/前端） | 回归风险 | 保留非流式回退分支（`llm_stream_enabled` 开关） |
| 缓存失效边界 | 用户改模板/词库后候选陈旧 | `config_version` 联动清空缓存 |
| 异步词频落盘 | 进程异常退出丢数据 | 启动时 flush + 退出钩子 |
| 流式 SSE 解析 | 部分代理不兼容 | 探测失败自动回退非流式 |
| 焦点检测降频 | 漂移检测延迟 | 间隔可配，默认 5 字保守 |
